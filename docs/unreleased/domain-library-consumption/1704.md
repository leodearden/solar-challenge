`GridServicesEventsConfig` gains three last fields, so its positional
construction is unchanged. `participation`, default `"observed"`, is held as the
`gridservices.EventParticipation` member it names: `observed`, the fleet runs its
own dispatch and is priced from the spare capacity it leaves, or `dispatched`,
the fleet is enrolled, each battery home discharging at full power through each
drawn event window; any other value is refused naming
`GridServicesEventsConfig.participation` and both values.
`gridservices.EventParticipation`, reached through that field, is a `StrEnum`
whose `parse(value, *, what)` returns the member a value names and refuses
anything else as `GridServicesBand.parse` does. `event_day_seed`, default `0`,
is the seed the fleet's event days are drawn with, a whole number of at least 0,
refused naming `event_day_seed`. `site_export_limit_kw`, default `None` for no
limit, is the most a home may export in a step in which its battery exports, PV
excess included, a finite number of at least 0, refused naming
`site_export_limit_kw`, and read only when the fleet is dispatched; it does not
curtail PV export in a step in which the battery exports nothing. A `capacity_at_events` block reads each as a key of
the same name; a null `participation` or `event_day_seed` is refused, and a null
`site_export_limit_kw` is no limit. The 0.6.0 tag has none of these. Consumers
need no change when they re-pin.

`gridservices.drawn_event_days(window, days, seed, *, position)` returns the
days of `days` on which an `EventWindow`'s events fall, sorted: a day is
eligible when its month and weekday are among the window's, and the count is
`events_per_year` times the share of each calendar year's eligible days that
`days` holds, computed exactly and rounded half up, then at least 1 when any day
is eligible and at most the eligible days, so a full calendar year draws exactly
`events_per_year`. `days` is read as a set of dates, each exactly a `date`, a
`datetime` refused naming `days[i]`, by `dispatch.as_event_days`, the reader
`dispatch.EventDischargeWindow` reads its days with, now public. The keyword-only
`position` is the window's index in its configuration's `event_windows`, which
the seed is combined with, so each window draws from its own stream; `seed` and
`position` are whole numbers of at least 0, refused naming each. The same
arguments draw the same days from a generator of the draw's own, which reads
and advances no home's random stream and neither global generator. Neither name
joins `solar_challenge.__all__`.

`BatteryConfig` gains a last field, `site_export_limit_kw`, default `None` for no
limit: the most the home may export in a step in which the battery exports, PV
excess included, a finite number of at least 0, refused naming
`site_export_limit_kw`. It does not curtail PV export in a step in which the
battery exports nothing. A battery has no YAML key for it, so `scenario_writer`
refuses a battery that sets it, naming `site_export_limit_kw`.
`dispatch.StepLimits.for_step` gains keyword-only `site_export_limit_kw`, default
`None`: its `max_export_kw` is then also no more than the limit less the step's PV
excess, or 0, and with `None` it is exactly as before. `StepLimits.require_admissible`
names the export bound "the discharge limit's headroom after the step's
shortfall, within any site export limit less the step's PV excess".
`dispatch.EventDischargeStrategy`, `dispatch.with_event_discharge` and
`dispatch.build_dispatch_strategy` gain keyword-only `site_export_limit_kw`,
default `None`, read as a finite number of at least 0: inside a window the
strategy then asks exactly that reduced export limit, and it must equal the
battery's `BatteryConfig.site_export_limit_kw` for as long as it is used.
`Battery` gains a read-only property, `site_export_limit_kw`, its config's limit,
and `simulate_timestep` judges each step's decision against it, so a strategy that asks more is refused before the battery moves;
`simulate_home` and `simulate_community` wrap a battery's windows at its limit.
A battery with no limit runs exactly as before.

`config.ScenarioConfig.simulated_homes` enrols a dispatched fleet: when the
scenario's `finance.grid_services_model` is a `GridServicesEventsConfig` whose
`participation` is `dispatched`, every home with a battery is simulated with
`BatteryConfig.event_discharge` set to one `dispatch.EventDischargeWindow` per
event window that draws a day of the period (the days
`drawn_event_days(window, the period's dates, event_day_seed, position=i)`
gives, in the window's hours) and with `BatteryConfig.site_export_limit_kw` set
to the configuration's limit; a home with no battery is unchanged. With any
other participation or pricing it returns the homes as before. A
`ScenarioConfig` whose events configuration is dispatched but none of whose
homes has a battery is refused at construction, and by a `map_homes` that
strips every battery, with a `ConfigurationError` naming the scenario and
`finance.grid_services_model.participation`. Enrolment changes no pricing yet:
a dispatched configuration's events income is still
`compute_grid_services_at_events`' spare-capacity pricing of the enrolled run,
so under the `operational` baseline a drawn day, on which each battery already
discharges at full power, adds next to no spare capacity. The 0.6.0 tag enrols
no home.
